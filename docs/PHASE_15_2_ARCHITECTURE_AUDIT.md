## 1. Executive Summary

This audit establishes the comprehensive technical specification and implementation plan for resolving **Finding F-02 (Unpartitioned Artifact Namespace)**, classified as **P0 (Critical Architectural Blocker)** in `docs/PHASE_15_ARCHITECTURE_AUDIT.md`.

Phase 15.1 established PostgreSQL as the authoritative durable PlanStore (`85daba8`, `75afd6b`), solving cold-boot TaskGraph reconstruction and eliminating the Recovery Cliff (Finding F-01). However, runtime execution artifacts generated by workers continue to be stored in an unpartitioned directory layout where `space_id` is omitted from the filesystem path.

### The Core Vulnerability (F-02)
Currently, capability workers construct artifact paths using:
```text
<base_working_dir>/artifacts/repository/<task_id>_*
<base_working_dir>/artifacts/test_runner/<task_id>_*
<base_working_dir>/artifacts/research/<task_id>_*
```
Because `space_id` is omitted, two independent Spaces executing tasks with identical task identifiers (e.g., `task-001`, `task-inspect`, `task-test`, `task-research-1`) write to identical filesystem locations. This allows:
1. **Silent Overwrite:** Space B silently overwrites Space A's manifests, diffs, test logs, and research data.
2. **Cross-Space Read / Information Leakage:** Space B can read Space A's artifacts.
3. **Evidence Invalidation:** `DeterministicGoalEvaluator` encounters unexpected SHA-256 mismatches or evaluates fraudulent evidence because another Space mutated the file.
4. **Cross-Space Destruction:** Cleanup routines in Space B delete artifacts belonging to Space A.
5. **Violation of SCCA Laws 1, 2, and 4:** Operations and state escape the Space boundary.

This audit provides an exhaustive analysis of all producers, consumers, path resolvers, security vectors, and test requirements, presenting a minimal, backwards-compatible, and Core-Independent target architecture.

## 4. Current Artifact Architecture & Execution Flow

```text
SpaceKernel (Space A)            SpaceKernel (Space B)
     │                                │
     ▼                                ▼
Dispatcher                       Dispatcher
     │                                │
     ▼                                ▼
RuntimeWorkerInvoker             RuntimeWorkerInvoker
     │                                │
     ▼                                ▼
Workers (base_working_dir)       Workers (base_working_dir)
     │                                │
     └──────────────┬─────────────────┘
                    │ (No space_id namespace)
                    ▼
          UNPARTITIONED DISK
   <base_working_dir>/artifacts/
   ├── repository/<task_id>_manifest.json     <── COLLISION / OVERWRITE
   ├── repository/<task_id>_patch.diff        <── COLLISION / OVERWRITE
   ├── test_runner/<task_id>_test_report.json <── COLLISION / OVERWRITE
   └── research/<task_id>_raw.txt             <── COLLISION / OVERWRITE
```

### Path Construction Failure Path
1. `DeterministicDispatcher.execute_task_full_pipeline` takes `base_dir: Path | None`.
2. `RuntimeWorkerInvoker` holds `self.base_working_dir: Path | None = None`.
3. Workers (`RepositoryWorker`, `TestRunnerWorker`, `ResearchWorker`) receive `base_working_dir` at instantiation.
4. When executing an `ExecutionRequest`, workers have access to `request.space_id`.
5. However, each worker ignores `request.space_id` during artifact path generation and executes:
   ```python
   art_dir = self.base_working_dir / "artifacts" / "<worker_type>"
   art_path = art_dir / f"{request.task_id}_<filename>"
   ```
6. The resulting absolute path is stored in `Artifact.path` and returned to the dispatcher.
7. `DeterministicDispatcher._is_safe_artifact_path` attempts to verify:
   ```python
   space_root = (base_dir / space_id).resolve()
   resolved.relative_to(space_root)
   ```
8. Because `art_path` does not contain `space_id`, `resolved.relative_to(space_root)` raises `ValueError`.
9. `_is_safe_artifact_path` catches `ValueError` and falls back to:
   ```python
   resolved.relative_to(base_dir.resolve())
   ```
10. The unpartitioned path is accepted, effectively bypassing the Space boundary.

## 7. Space Boundary Analysis (SCCA Laws 1, 2, 4)

### 7.1 Collision Trace Scenario
Suppose Space `alpha` and Space `beta` run concurrently or sequentially on a single node sharing `base_working_dir = /tmp/ryu`:
- **Step 1:** Space `alpha` executes `task-inspect` under `repository.inspect`.
  - Artifact created: `/tmp/ryu/artifacts/repository/task-inspect_manifest.json`
  - SHA-256: `hash_alpha_123`
  - Evidence created: `VerifiedExecutionEvidence(task_id="task-inspect", path="...", sha256="hash_alpha_123", space_id="alpha")`
- **Step 2:** Space `beta` executes `task-inspect` on a completely different repository.
  - Artifact created: `/tmp/ryu/artifacts/repository/task-inspect_manifest.json` (OVERWRITES file from Step 1)
  - SHA-256: `hash_beta_456`
- **Step 3:** Space `alpha` executes goal evaluation requiring verification of its manifest.
  - Evaluator re-reads `/tmp/ryu/artifacts/repository/task-inspect_manifest.json`.
  - File contains `hash_beta_456` instead of `hash_alpha_123`.
  - **Result:** SHA-256 mismatch failure (`EvidenceStatus.TAMPERED`), falsely reporting malicious tampering.
- **Step 4:** Space `beta` fails and performs cleanup, deleting `/tmp/ryu/artifacts/repository/task-inspect_manifest.json`.
  - Space `alpha` attempts replay or recovery.
  - **Result:** File missing on disk (`Artifact not found on disk`).

### 7.2 SCCA Law Evaluation
- **Law 1 (Everything happens inside a Space):** VIOLATED. File writes occur in shared global directories outside any Space namespace.
- **Law 2 (Capabilities are requested, never owned):** VIOLATED. Space `beta` mutates artifacts produced under capability grants issued exclusively to Space `alpha`.
- **Law 4 (Knowledge belongs to the Space first):** VIOLATED. Research raw texts and synthesis notes written by Space `alpha` are visible in the shared directory to Space `beta`.

## 8. Path Construction Audit & Directory Traversal Vulnerabilities

### Current Path Construction Code
In all Phase 14 workers:
```python
art_dir = self.base_working_dir / "artifacts" / "<worker_type>"
art_dir.mkdir(parents=True, exist_ok=True)
output_path = art_dir / f"{request.task_id}_<suffix>"
```

### Vulnerability Analysis
1. **Missing `space_id`:** Neither `art_dir` nor the filename incorporates `space_id`.
2. **Missing Input Sanitization:** `request.task_id` is incorporated directly into the filename: `f"{request.task_id}_manifest.json"`.
   - If an adversarial task ID contains `../../etc`, it could escape `art_dir`.
   - In Windows environments, `..\..\` or drive letters (`C:`) could redirect the write.
3. **Dispatcher Fallback Hole (`dispatch_model.py:1616`):**
   ```python
   try:
       resolved.relative_to(space_root)
   except ValueError:
       try:
           resolved.relative_to(base_dir.resolve())
   ```
   Accepting any path under `base_dir.resolve()` destroys multi-space isolation when spaces share `base_dir`.

## 11. Artifact ID vs Artifact Path

### Current State
In `workers/contract.py`:
```python
@dataclass
class Artifact:
    artifact_id: str
    name: str
    path: str
    mime_type: str = "text/plain"
    size_bytes: int = 0
    sha256: str = ""
    metadata: dict[str, Any] = field(default_factory=dict)
```
- `artifact_id` is an execution-scoped identifier: `f"art-{task_id}-test-report"`.
- `path` is the physical filesystem path string.
- `name` is the logical filename.
- **Architectural Observation:** The `Artifact` dataclass currently lacks a first-class `space_id: str` field, forcing downstream verifiers to inspect `metadata` or trust context.

### Recommendation
Add `space_id: str = ""` to `Artifact` (with sensible default for backward compatibility) and ensure workers populate it from `request.space_id`.

## 12. Persistence, Restart, and Recovery Analysis

### Durable Records Established in Phase 15.1
1. **`plans` table:** Stores `TaskGraph` JSONB. Nodes record `result_ref: str | None` (e.g., `artifact://...` or task attempt ID).
2. **`execution_attempts` table:** Stores `artifact_sha256: VARCHAR(128)`, `task_id`, `space_id`, `plan_version`.
3. **`VerifiedExecutionEvidence`:** In-memory dataclass containing `path: str`, `sha256: str`, `space_id: str`.

### Recovery Lifecycle After Process Restart
1. `StartupRecoveryEngine` recovers interrupted tasks from `execution_attempts`.
2. When the runtime evaluates whether a task succeeded or failed before restart, it checks `artifact_sha256`.
3. If an artifact must be re-read from disk after restart (e.g., during replay or detailed inspection), the system must reconstruct the path:
   $$\text{Path} = \text{base\_dir} / \text{"artifacts"} / \text{space\_id} / \text{worker\_type} / \text{filename}$$
4. With space-partitioning, the path is completely deterministic, unambiguous, and safe across restarts.

### 13.2 Centralized Artifact Path Authority
Rather than having each worker independently duplicate path formatting and sanitization, we define a centralized, deterministic resolver:

```python
# core/space/artifact_paths.py (Core-Independent)

def get_space_artifact_dir(
    base_dir: Path | str,
    space_id: str,
    worker_type: str,
) -> Path:
    """Return the canonical, sandboxed artifact directory for a given space and worker."""
    sanitized_space = sanitize_path_component(space_id)
    sanitized_worker = sanitize_path_component(worker_type)
    p = Path(base_dir).resolve() / "artifacts" / sanitized_space / sanitized_worker
    p.mkdir(parents=True, exist_ok=True)
    return p

def resolve_artifact_path(
    base_dir: Path | str,
    space_id: str,
    worker_type: str,
    filename: str,
) -> Path:
    """Return an absolute, validated path for an artifact within a space."""
    art_dir = get_space_artifact_dir(base_dir, space_id, worker_type)
    clean_filename = sanitize_filename(filename)
    resolved = (art_dir / clean_filename).resolve()
    # Verify strict containment within art_dir
    resolved.relative_to(art_dir)
    return resolved
```

### 13.3 Hardening `DeterministicDispatcher._is_safe_artifact_path`
Eliminate the security bypass in `core/orchestrator/dispatch_model.py`:
- Remove `resolved.relative_to(base_dir.resolve())` fallback.
- Require all artifact paths to resolve strictly under `base_dir / "artifacts" / space_id` (or `base_dir / space_id`).
- Fail closed with `Artifact path escapes space sandbox boundary` if an artifact does not belong to the task's space.

## 16. Platform & Windows-Specific Analysis

1. **Path Separators:** Path construction must use `Path` objects and forward-slash normalization to behave identically across Windows and POSIX/WSL.
2. **Windows Path Length Limits:** On Windows, deep path nesting (`C:\Users\...\artifacts\<space_id>\<worker_type>\<task_id>_...`) can approach `MAX_PATH` (260 characters). Sanitization must ensure task IDs and filenames are bounded (e.g. maximum 64 characters).
3. **Reserved Names:** Windows forbids reserved names (`CON`, `PRN`, `AUX`, `NUL`, `COM1..9`, `LPT1..9`). The filename sanitizer must disallow reserved names.
4. **Drive Letter Injection:** The resolver must reject filenames containing `:` to prevent Windows drive-letter escaping.

## 17. Concurrency Analysis

While concurrent DAG scheduling (Finding F-04) is deferred to Phase 16, concurrent execution of multiple Spaces on a single daemon or test runner is an active requirement.
- **Current Behavior:** Space A and Space B executing concurrently race on shared filenames.
- **Target Behavior:** Space A writes to `artifacts/space_A/...` while Space B writes to `artifacts/space_B/...`.
- **Concurrency Safety:** Because directories are fully disjoint at the OS filesystem level, concurrent file operations execute without locks, contention, or cross-space interference.
