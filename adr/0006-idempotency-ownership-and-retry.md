# ADR 0006: Idempotency Ownership and Provider Stored-Response Semantics

## Status
Accepted

## Context
In RYU AI Space-Centric Cognitive Architecture (SCCA) §10, failure recovery relies on retries across bounded attempts for transient failure classes (`transient.timeout`, `transient.rate_limit`, `transient.network`). Every retry must reuse the original request's `idempotency_key`.

Law 6 dictates: *Failures Are Contained, Escalated, and Never Silent*. Side-effecting operations (such as credit card charges, disk writes, external API mutations, or resource lease allocations) must not execute more than once when retried after network timeouts or client disconnects. Contract Matrix item **OPEN-003** asks: *Who is the exact authoritative owner of the idempotency guarantee?*

## Decision

1. **Authoritative Ownership at Execution Boundary:**
   - The authoritative owner of the idempotency guarantee is the **boundary component that directly executes the side effect**.
   - Specifically:
     - **For Resource Leases / Allocations:** The `ResourceManager` is the authoritative owner. It maintains an idempotency registry keyed by `(space_id, requester_id, idempotency_key)`. A retry with an existing active key immediately returns the previously issued `Lease` without decrementing additional capacity or creating a duplicate lease token.
     - **For Tool & Capability Providers (e.g., `payment.charge`):** The capability provider / worker adapter is the authoritative owner. It persists or caches `{ (space_id, idempotency_key) -> CapabilityResponse }`.
     
2. **Stored-Response Semantics:**
   - When an operation is executed for the first time with an `idempotency_key`, the provider performs the side effect and stores the resulting response.
   - On any subsequent attempt carrying the same `idempotency_key`:
     - The side-effect execution is short-circuited.
     - The stored `CapabilityResponse` is returned with an indicator/status confirming it is a cached result.
     - Zero additional side effects are triggered.

3. **Key Stability and Propagation:**
   - The `idempotency_key` is generated at the initial caller / requester boundary (e.g. `CapabilityRequest.idempotency_key`).
   - Retries generated by the failure escalation loop MUST NOT generate a new idempotency key; they must propagate the original key unmodified.
   - If an operation fails with a `terminal.*` error class (e.g., `terminal.invalid_params`, `terminal.permission_denied`), retries are disallowed by the Failure Taxonomy (§10), preventing key pollution.

4. **Crash Recovery & Concurrency:**
   - Under concurrent duplicate requests with the same `idempotency_key`, atomic check-and-set semantics guarantee that only one thread/worker performs the execution; the competing thread awaits the stored result or receives the stored response once committed.
   - In-flight operations checkpoint the idempotency key so that process restart reconciles pending operations without duplicated side effects.

## Consequences
- Resolves CONTRACT_MATRIX OPEN-003.
- Guarantees exactly-once side effects for retried capability calls and resource acquisitions.
- Clear separation of concerns: Resource Manager handles resource leases; Tool providers handle external capability side effects.
